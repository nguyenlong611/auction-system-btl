Adjuge — Project Overview

Online Auction System • JavaFX • 32 Java files • 6 packages

1. The Big Picture (30-second version)

What does this app do?

Users can browse auctions, sign in, place bids, and list items for sale. When an auction's timer runs out, the highest bidder wins. Think of it like a simplified eBay.

How it's structured (MVC Pattern)

User clicks button → FXML (View) → Controller → Service (Logic) → DataStore (Data)

That's it. Every action in the app follows this flow. The View shows things, the Controller handles clicks, the Service does the logic, and the DataStore holds all the data.

3. The Class Hierarchy (THE EXAM QUESTION)

This is what the teacher will ask about. There are two inheritance trees, both starting from Entity:

Entity (abstract — has id, createdAt, printInfo(), getDisplayName())
│
├── Item (abstract — has name, price, image, condition)
│   │   abstract methods: getCategoryLabel(), getItemSpecifics()
│   │
│   ├── Electronics  — brand, model, warranty      → "ELECTRONICS"
│   ├── Art           — artist, year, medium       → "ART & COLLECTIBLES"
│   ├── Vehicle       — make, model, mileage       → "VEHICLES"
│   ├── Fashion       — brand, material, size      → "FASHION"
│   ├── Antique       — era, origin, age           → "ANTIQUES"
│   └── MusicalInstrument — brand, year, type     → "MUSICAL INSTRUMENTS"
│
└── User (abstract — has name, email, password)
    │   abstract methods: getRole(), canBid(), canSell(), canManageUsers()
    │
    ├── Bidder  — canBid()=true,  canSell()=false, canManageUsers()=false
    ├── Seller  — canBid()=true,  canSell()=true,  canManageUsers()=false
    └── Admin   — canBid()=false, canSell()=false, canManageUsers()=true
How to explain this to your team:

"Entity is the grandparent. Item and User are the parents. Everything else is a child."

Every child inherits fields from its parent (like id, name) and overrides abstract methods to give its own answer. That's inheritance + polymorphism.

4. Polymorphism — The 5 Examples to Memorize

Polymorphism = same method name, different behavior depending on the object type.

Example 1: getCategoryLabel()

Declared in Item (abstract). Each subclass returns a different string:

Item item = new Electronics(...);
item.getCategoryLabel();  // → "ELECTRONICS"

Item item2 = new Art(...);
item2.getCategoryLabel(); // → "ART & COLLECTIBLES"

// Same method, different result. That's polymorphism.
Example 2: canBid()

Declared in User (abstract). Each user type answers differently:

User user = new Bidder(...);
user.canBid();  // → true

User user2 = new Admin(...);
user2.canBid(); // → false

// We call the SAME method on a User variable,
// but the answer depends on the ACTUAL type.
Example 3: printInfo()

Every single class overrides this. You can loop through a list and get different outputs:

List<Entity> all = List.of(new Electronics(...), new Bidder(...), new Art(...));
for (Entity e : all) {
    System.out.println(e.printInfo());  // Different output each time!
}
Example 4: ItemFactory (Factory Pattern + Polymorphism)

The factory returns Item, but creates the correct subtype:

Item item = ItemFactory.createItem(Category.ELECTRONICS, "MacBook", ...);
// item is actually an Electronics object
// but we hold it in an Item variable — polymorphism!
Example 5: Auction holds Item (any subtype)

The Auction class has a field Item item. It doesn't care if it's Electronics, Art, or Vehicle:

Auction auction = new Auction(..., new Vehicle(...), ...);
auction.getItem().getCategoryLabel();    // → "VEHICLES"
auction.getItem().getItemSpecifics();    // → "1965 Ford Mustang | 45,000 mi"

// The Auction doesn't know or care what type of Item it holds.
// It just calls the methods. The Item handles the rest.

5. Design Patterns — 6 Patterns Used

SINGLETON DataStore

What: Only ONE instance exists in the whole app.

Where: DataStore.getInstance()

Why: All services need to access the same data. If we had multiple copies, data would go out of sync.

How to spot: Private constructor + static getInstance() method.

FACTORY METHOD ItemFactory

What: Creates the right Item subtype based on a category.

Where: ItemFactory.createItem(category, ...)

Why: The controller doesn't need to know which class to use. It just says "make me an item in this category" and the factory decides.

OBSERVER AuctionObserver

What: When a bid is placed, all watchers get notified automatically.

Where: Auction.addObserver(), BiddingController implements AuctionObserver

Why: The UI updates in real-time without polling. When a bid happens, the auction tells the controller, and the controller refreshes the screen.

STRATEGY BidValidationStrategy

What: Validation rules are in a separate class that can be swapped.

Where: BidService uses StandardBidValidator

Why: If we want different rules (e.g., VIP users can bid lower), we just swap the strategy. No need to change BidService.

MVC Model-View-Controller

What: Separates the app into three responsibilities.

Where: model/ = Model, bidding.fxml + bidding.css = View, BiddingController = Controller

Why: The FXML never touches data. The model never touches UI. The controller connects them. Changing the UI doesn't break the logic.

DAO Data Access Object

What: Each database table has its own class for SQL operations.

Where: UserDAO, ItemDAO, AuctionDAO, BidDAO

Why: Business logic (DataStore, BidService) never writes raw SQL. It just calls auctionDAO.insert(a). If we switch from SQLite to MySQL, only the DAO classes change.

6. How Key Features Work

1 User clicks "Sign In"
Button click → Controller.onLogin() → AuthService.login(email, pass) → DataStore.getUserByEmail()

If password matches → store user in session, go to home. If not → show error message.

2 User places a bid
Click "Bid" → Controller.onPlaceBid() → BidService.placeBid() → synchronized{validate + save} → Auction.notifyObservers() → Controller.onNewBid() → refresh UI

synchronized prevents two people from bidding at the exact same time (race condition).

3 User creates a listing
Fill form + click "List" → Controller.onCreateAuction() → ItemFactory.createItem(category) → AuctionService.createAuction()

Factory Method creates the right Item subtype (Electronics, Art, etc.) based on the selected category.

4 Auction expires automatically
AuctionTimerService (background thread) → Checks every 1 second → If expired → state = FINISHED → Observer notifies UI

9. Thread Safety (Concurrency)

The Problem

Two people bid at the exact same millisecond. Without protection, both bids could "win" or one could be lost.

Our Solution

In BidService.placeBid(), we use synchronized(auction). This means:

  • Only ONE thread can bid on a specific auction at a time
  • The second bidder waits until the first one finishes
  • Different auctions can still be bid on in parallel (we lock per-auction, not globally)

We also use ConcurrentHashMap in DataStore so multiple threads can read/write users and auctions safely.
